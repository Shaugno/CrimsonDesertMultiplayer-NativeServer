Remaining P1: an exception during second-hook creation bypasses hook cleanup
File: tools/pkt3576/capture.cpp, lines 630-631, and PreHookRollback at 591-602.

SafetyHook::MidHook::create is not noexcept. Its inline-hook setup constructs
vectors (for example desired_addresses) and can throw std::bad_alloc rather
than return an expected error. Both install_slot calls are outside a catch.

When send-hook creation throws after receive-hook installation, PreHookRollback
disarms the observer, closes the file, and clears g_active, but does not disable
and quiesce the receive hook. running is still false, so stop returns Idle and
release_owner can delete the State without the backend's quiescence protocol.
The receive entry is still patched until that deletion. With active callers,
hook/callback storage may be freed before they have finished.

Reproduction
build/review_capture_hook_allocation.cpp links the real capture backend and
dummy target functions. A replacement operator new injects one bad_alloc only
after the dummy receive entry is patched. This fails an 8-byte allocation in
the subsequent hook setup, not the initial output-buffer reserve.
Observed:
hook allocation injected=1 size=8 escaped=1 receive_still_patched=1 stop_idle=1
Exit 93 is the harness's failure verdict. No concurrent callback crash or game
crash is claimed; the escaped exception and untracked installed hook were
directly reproduced in the game-free test executable.

Requested fix
Make all fallible installation stages exception-safe, including both SafetyHook
factory/enable calls. Before disarming/freeing state or clearing g_active,
disable and quiesce every live hook using the existing cleanup protocol.
If that cannot be completed, return Retained and preserve all required state
and code. An allocation exception must not leave a live hook with stop==Idle.
Add tests for allocation failure during the first and second hook setup and
for recovery/retry, beyond the existing records.reserve test. Re-run the suite.

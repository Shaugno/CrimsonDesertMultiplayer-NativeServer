Additional packet-header analysis
Using the existing common/troc_frame parser's five-byte layout as a hypothesis:
 u16 little-endian opcode | signed slot byte | u16 little-endian payload length
All 70 records satisfy payload_length + 5 == raw stack-u16 packet length.
All prefix lengths equal min(packet_length, 16). These checks support that
the candidate hooks see framed packet buffers and the sampled length is
consistent. They do not validate unrecorded payload bytes or message meaning.
Stored send slots are 0; receive slots are -1.

Limits / observations
The walking log retains just the first 64 records; it is not representative
of all 3486 counted observations or their order across the entire window.
Only up to 16 prefix bytes were saved. There are no per-record timestamps,
so action timing, actor identity, coordinates, and complete payload layouts
cannot be established from these files. Other actors/background activity can
also contribute traffic. No movement name is adopted from frequency alone.
The pre-stop status counters of zero are cached snapshots in live_runner;
status() does not refresh them from the active capture. Final stop counters
and archived records agree. This does not invalidate the captured records;
do not use an active zero counter to conclude that no traffic was observed.

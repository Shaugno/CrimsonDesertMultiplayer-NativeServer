## Initialization determines the component stream

At 0xCC8E5B0-0xCC8E5CC, initialization follows actor+0x88 to its descriptor,
takes the object at descriptor+8 and selector byte at descriptor+1, and calls
that object's virtual +0x38 with the actor. The concrete factory target and
its per-class component inventory remain unresolved.

At 0xCC8E5CF-0xCC8E614 it iterates the pointer slots at actor+0x68, count
actor+0x70. Each non-null component receives virtual +0x18 with actor and
descriptor. A nonzero returned error branches to 0xCC8E6D6, logs the error,
and returns it. This routine alone does NOT prove failed initialization is
rolled back; the owning caller and later destruction must be traced.

After successful initialization, 0xCC8E630-0xCC8E6AE builds actor+0x78's
16-byte entries in ascending slot order. Each entry carries a component
pointer and the slot index at entry+8; actor+0x80 is the compact entry count.
These are native memory records, NOT 16-byte wire components.

The user/body deserializers iterate that compact list and invoke component
virtual +0x58 against the shared reader. The body loop's computed stride
resolves to 16 in this file, agreeing with its literal loop increment.
There is no demonstrated generic wire component length or component ID here.
Consequently, an empty list or guessed fixed sizes cannot certify spawn data.

The user actor dispatch success branch additionally calls component virtual
+0x68 for entries whose component+0x12 byte is zero, then sets that byte on
success (0x9D6B10-0x9D6B42). This is a separate phase after deserialization;
it must not be equated with allocation or initial virtual +0x18 success.

## Body relation tail

After the component loop, 0xB846AC9-0xB846BBB consumes a raw dword into
actor+0xAC, a u16 count, and that many dwords into the vector at actor+0xB0.
The computed count destination resolves to stack+0x90 in the file, matching
the subsequent count reads. The vector count is actor+0xB8.

The new `decode_body_relation_tail` helper parses ONLY an already isolated
tail with this shape. It requires exact consumption and caps allocation at
256 keys as a diagnostic policy. It keeps raw values and duplicates intact.
It neither locates the tail nor validates the preceding components. No
production caller connects it to a spawn path. The component endpoint must
be independently established; scanning backward for a plausible count is
not a valid substitute.

0x198F780 removes the matching raw key from the relation vector using
swap-with-last and decrements the count under its lock. Array ordering thus
cannot be assumed stable across removals. This supports a relationship-list
interpretation; it does not establish cross-machine ownership semantics.

## Cleanup order and deferred execution

All three assessed actor vtables' +0x118 slots resolve through 0x2294DB0 to
0xCC88D60. Continuation 0xCC88D77 indexes the compact component list as
count-minus-index-minus-one. It calls each component's virtual +0x38 in
REVERSE order. Nonzero results are logged, but iteration continues. This is
component cleanup, not proof of final deallocation or destructor behavior.

Detach 0x9CA890 has both a direct virtual +0x118 path and a callback path.
The callback 0x9DDEB0 -> 0x9CAD90 -> 0x9742160 reaches virtual +0x118 at
0x974228E and writes completion byte 2 afterward. Callback scheduling,
reference ownership, cancellation and game-thread requirements still need
characterization. A future backend must not free the actor merely because
detach or registry removal returned.

The remove transition 0xCC82570 updates state under a lock, invokes +0x80,
releases that lock, then invokes +0x110. These ordering observations are not
authorization to call these functions from a networking thread.
